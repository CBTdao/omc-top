What is agent observability (and why does it bill per step)?

Plain-English definition · Updated 2026-11-24. Primary sources: the OpenTelemetry semantic conventions for generative AI systems (official docs and OTel blog, checked 2026-11-24) and Langfuse's official pricing page and billable-units FAQ (checked 2026-11-24).

The 30-second answer

Agent observability is the practice of recording what an AI agent actually did — every model call, tool invocation, token count, latency and evaluation score — as structured telemetry you can query per step, rather than as flat log lines. The vendor-neutral format is OpenTelemetry's semantic conventions for generative AI, whose official documentation still carries Development status in 2026, with version switches gated behind an OTEL_SEMCONV_STABILITY_OPT_IN environment variable. By default that telemetry captures no prompt content — only metadata like model names, token counts and durations. The platforms that collect it bill per data point: Langfuse's official pricing page defines a billable unit as any tracing data point you send — the trace, the observations inside it, the scores attached to it — with 100k units included at $29/month and overage at $8 per 100k. One agent interaction can emit twenty or more data points, so the observability bill scales with step count, not user count.

What does agent observability actually mean?

Agent observability is the instrumentation layer that answers three questions about an autonomous AI workflow: what happened (which model calls and tool calls ran, in what order, nested under which agent loop), how much it cost (input and output tokens per call, multiplied by the model's rates), and why it went wrong (errors, timeouts, finish reasons, the exact prompt that produced a bad answer). A chatbot log tells you what the user saw; agent telemetry tells you every intermediate decision the agent made on the way there.

The vendor-neutral format is the OpenTelemetry semantic conventions for generative AI systems. Per the official documentation, the conventions cover five signals — events, exceptions, metrics, model spans and agent spans — plus provider-specific pages for Anthropic, Azure AI Inference, AWS Bedrock and OpenAI. A single interaction renders as a span tree: a top-level invoke_agent span with child chat spans for each model call and execute_tool spans for each tool invocation, carrying attributes such as gen_ai.request.model, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens and gen_ai.response.finish_reasons. Token metrics are recorded against recommended histogram bucket boundaries that run from 1 up to 67,108,864 tokens — a range wide enough to hold both a chat reply and a context-window-sized retrieval, per the official metrics spec.

Two details in the spec matter commercially. First, content is opt-in: the official OTel blog states that "by default, no prompt content or tool arguments are captured with GenAI telemetry, as these can contain sensitive data. Only metadata like model names, token counts, and durations are included." Second, billed tokens win: the official metrics spec instructs that when a system reports both used tokens and billed tokens, the instrumentation must report the billed ones — the spec itself acknowledges that what the model used and what the invoice says can differ.

What does agent observability cost in 2026?

The standard is free; the platform is metered per data point

The OpenTelemetry conventions are an open standard with no license fee — but they only define the wire format. Collecting, storing and viewing the telemetry is what you pay for, and the platforms that do it meter per data point, not per seat and not per token. Langfuse's official pricing page defines the unit precisely: "a billable unit in Langfuse is any tracing data point you send to our platform — this includes the trace (a complete application interaction), observations (individual steps within a trace: Spans, Events and Generations), and scores (evaluations of your AI outputs)."

Langfuse's official price ladder (checked 2026-11-24)

On its official pricing page, Langfuse publishes: Hobby — free, all platform features with limits, 50,000 units/month included, 30 days data access, 2 users, 1,000 ingestion requests/min. Core — $29/month, 100,000 units included, additional usage at $8 per 100k units with volume tiers stepping down to $7 (1M–10M), $6.50 (10M–50M) and $6 (50M+), 90 days data access, unlimited users, 4,000 requests/min. Pro — $199/month with 3 years data access and 20,000 requests/min. Enterprise — $2,499/month with audit logs, SCIM, SSO and custom rate limits, plus an optional Teams add-on at $300/month. Langfuse is also open source and can be self-hosted free — its own FAQ confirms it — which moves the cost from subscription to the servers and engineering time you spend running the pipeline yourself.

The arithmetic: step count is the bill multiplier

Count the data points one agent interaction emits under this definition: one trace, ten model generations (one per reasoning step), ten tool spans (one per tool call), five evaluation scores. That is 26 billable units for one user-visible answer (our arithmetic on Langfuse's own unit definition). At the Core plan's included 100k units, that budget buys roughly 3,800 such interactions per month — about 128 per day — before overage starts at $8 per additional 100k units, or $0.08 per 1,000 data points. A support bot that answers in one generation and no tools emits 1–2 units for the same interaction; an agentic workflow emits twenty times that. The same 100k-unit budget that covers a month of chat traffic can cover a week of agent traffic.

Why does it matter when you're choosing a tool?

First, because observability is the only honest cost ledger for an agent. Per-model price lists tell you what a token costs; only step-level telemetry tells you how many tokens an agent actually burned across eleven retries and four tool calls before it produced the answer. The token metric spec's own "report billed tokens" rule exists because the gap between usage and billing is normal, and an agent multiplies that gap by every step it takes. If you cannot see the span tree, you are pricing an agent on its final answer, which is the least expensive thing it did.

Second, because the default telemetry is deliberately blind. Content capture — the actual prompts, tool arguments and tool results — is off by default for privacy reasons, and enabling it pipes customer text into a third-party platform's storage. That is the right default, but it means the debugging moments where you most want the exact prompt (the wrong-answer incident, the injection attempt) require a deliberate, governed opt-in. Budget for that decision before an incident forces it; the OTel blog notes that captured content lands in span attributes like gen_ai.input.messages and gen_ai.output.messages, which observability platforms may render as hard-to-read raw JSON unless they have GenAI-specific views.

Third, because the standard is not frozen, and the retention is the paywall. The OTel GenAI conventions remain in Development status as of 2026: instrumentations pin to version v1.36.0 by default, and moving to newer conventions requires the OTEL_SEMCONV_STABILITY_OPT_IN environment variable — meaning a dashboard you build this quarter may need re-wiring when the conventions stabilize. And on the platform side, the tier ladder is mostly a data-retention ladder: 30 days free, 90 days at $29, 3 years at $199. Regression analysis ("did the new prompt reduce tool failures?") needs history; the free tier forgets in a month.

What is true in 2026 specifically?

Is agent observability the same as model monitoring?

No. Model monitoring watches one API call: latency, tokens, error rate. Agent observability watches a tree: the agent loop, the workflow spans, every model and tool call nested underneath, tied together by a conversation ID so a session can be replayed end to end. The OTel agent-span conventions (agent creation, agent invocation, workflow invocation, tool execution) exist precisely because the single-call view cannot express an agent's branching. If a vendor's "agent observability" is a per-request latency chart, it is model monitoring with agent branding.

How do you estimate your unit count before signing up?

Instrument one representative interaction locally — a free tier or a self-hosted instance — and count the data points it emits: traces + observations + scores. Multiply by your expected monthly interactions and add 30–50% for retries and incident debugging, which you will do with content capture on, doubling the payload. The Langfuse pricing calculator on the official page shows the graduated tiers: the $8/100k headline rate steps down to $6/100k above 50M units, so the marginal cost falls with scale but never reaches zero.

Self-host or buy?

Self-hosting is free in license terms and is the right call when content capture must never leave your infrastructure — the SDKs (Python, JavaScript, OpenTelemetry) point at any OTLP endpoint. Buying the cloud plan buys the things that actually take engineering time: ingestion throughput (1,000 requests/min free vs 20,000 on Pro), dashboards, annotation queues, and the SSO/audit layer at Enterprise. The honest comparison is your on-call engineer's time against the $29–$2,499 ladder.

Quick checklist

  • Count data points, not users, before comparing platforms. One agent interaction = 1 trace + every generation + every tool span + every score; a 10-step loop can emit 20+ billable units per answer.
  • Check the retention line first. 30 days (free) cannot answer "did last month's change help?" — 90 days at $29/month or 3 years at $199/month is where regression analysis starts.
  • Decide the content-capture policy now, not during the incident. OTel defaults to metadata only; enabling prompt capture is a governed opt-in with privacy consequences.
  • Verify the billed-token rule in your dashboards. The spec says report billed tokens when both are available — your cost dashboards should reconcile against invoices, not model usage.
  • Ask what happens when the conventions stabilize. OTel GenAI is Development status with a version opt-in env var; pin your dashboards to attributes, not span names, where you can.
  • Test the export path. Batch export to your own storage and an open API are what make the telemetry portable; without them, observability data is a hostage.

The bottom line

Agent observability is step-level telemetry for AI agents — every model call, tool invocation and score recorded as structured data, standardized (still in Development status) by OpenTelemetry's GenAI conventions, which by default capture metadata only and gate content capture behind an explicit opt-in. Commercial platforms bill per data point: Langfuse's official pricing page includes 100k units at $29/month and charges $8 per additional 100k, and one agent interaction can emit 20+ units. Summary: observability of an agent costs like running one — estimate your unit count from step count, negotiate retention (30 days free forgets too fast), and treat content capture as a governance decision, not a debug checkbox.
