What is temperature in an LLM (and why is it disappearing in 2026)?

Plain-English definition · Updated 2026-11-04. Ranges, defaults and deprecation wording come from OpenAI's, Google's and Anthropic's own API references; the reading of what they add up to is ours.

AITop is an independent guide. Prices and features change fast — always check the vendor's page.

The 30-second answer

Temperature is the sampling parameter that decides how willing a language model is to pick a word that is not its first choice. It rescales the probability distribution over the next token: at 0 the model always takes the single most likely token, and as the value rises the distribution flattens so less likely tokens become reachable. The scale is not universal — OpenAI documents a range of 0 to 2 with a default of 1, Google documents 0.0 to 2.0 with a default of 1.0, and Anthropic documented 0.0 to 1.0 with a default of 1.0 — which is why "set temperature to 0.7" means different things on different platforms. The 2026 twist is that the parameter is being removed where it matters most: Anthropic's current reference marks temperature, top_p and top_k deprecated, with only the default value accepted on models released after Claude Opus 4.6 and every other value returning HTTP 400. Temperature never added knowledge, was never a guarantee of reproducibility, and is now optional on the models you would most want to control. The honest definition is narrower than the marketing: temperature changes which token gets picked, not how much the model knows.

What it actually means

Every token a language model emits starts as a score for every token in its vocabulary. Those scores become probabilities, and the model picks one. Temperature sits in the middle of that step: it divides the scores before the conversion, and the arithmetic has one visible consequence — low temperature sharpens the distribution toward the top token, high temperature flattens it toward the tail. The three providers describe the effect in almost the same words. OpenAI: "Higher values like 0.8 will make the output more random, while lower values like 0.2 will make it more focused and deterministic." Google: "A temperature of 0 means that the highest probability tokens are always selected." Anthropic's (now-deprecated) field description: "Use temperature closer to 0.0 for analytical / multiple choice, and closer to 1.0 for creative and generative tasks."

The numbers behind those sentences are where buyers get caught. OpenAI's field is documented as "between 0 and 2" with a default of 1. Google's documentation states that "Gemini models support a temperature value between 0.0 and 2.0" and that "models have a default temperature of 1.0," adding a detail most comparisons miss: "1.0 is the recommended starting value for temperature." Anthropic's field read "Defaults to 1.0. Ranges from 0.0 to 1.0." A 0.7 that feels restrained on GPT-class models is therefore already well above the midpoint on Claude-class models, and a 0.7 on Gemini is below the vendor's own starting point. Any prompt-engineering guide that hands you one number for all three is handing you a coincidence.

Temperature is also not the only knob, and the others are easier to misuse. top_p (nucleus sampling) keeps only the smallest set of tokens whose probabilities sum to that value and discards the rest; OpenAI describes 0.1 as "only the tokens comprising the top 10% probability mass are considered." top_k does the same thing by count rather than mass — Google documents top_k of 1 as greedy decoding, and current Gemini models list it as 64, fixed. Both platforms that expose both give the same instruction: OpenAI says "We generally recommend altering this or temperature but not both," and Anthropic labelled top_p and top_k "recommended for advanced use cases only." Turning two randomness dials at once does not give you finer control; it gives you a setting nobody can reproduce.

Why it matters when you're picking a tool

Because "we run at temperature 0" is the most common false claim in AI procurement. Every one of the three vendors says the same thing in its own words: Anthropic's field note read "even with a temperature of 0.0, the results will not be fully deterministic"; Google's parameter guide says a temperature of 0 is "mostly deterministic, but a small amount of variation is still possible"; OpenAI offers a seed parameter explicitly labelled Beta, promising only that the system "will make a best effort to sample deterministically," adding that "determinism is not guaranteed" and pointing developers at system_fingerprint to detect backend changes. If a vendor promises byte-identical output for a compliance, audit or regression-test use case, the parameter they are pointing at cannot deliver it — and if your acceptance testing depends on it, you find out in production.

Because the default is often not what your stack thinks it is. Consumer chat apps mostly do not expose temperature at all — Claude's app never did — while agent frameworks and IDE assistants ship their own defaults, commonly around 0.7 in orchestration libraries and 0 in some coding agents. Migrating a workflow from one harness to another can therefore change the sampling behaviour of every request without a single line of your prompt changing. This is the same class of invisible change as the rate-limit and reasoning-token asymmetries we document elsewhere: the knob you did not set is still setting your output.

Because temperature is not a quality dial. It cannot make a model produce a correct answer it does not already know — it only reshapes a distribution over tokens the model already scores. Google's own guide is unusually candid about the failure modes in both directions: if a response is "too generic, too short, or the model gives a fallback response, try increasing the temperature," and "if the model enters infinite generation, increasing the temperature to at least 0.1 may lead to improved results." Note what that second sentence implies: a low temperature can cause looping, which is the opposite of the intuition that turning randomness down makes output safer. Lower is not better; lower is narrower, and narrow has its own failure mode.

The 2026 reality check

The parameter is being withdrawn from the newest models. Anthropic's API reference now marks temperature, top_p and top_k deprecated, and the wording is specific enough to quote: "Models released after Claude Opus 4.6 do not support setting temperature. A value of 1.0 will be accepted for backwards compatibility, all other values will be rejected with a 400 error." top_p gets the same treatment with a wider tolerance — "a value >= 0.99 will be accepted for backwards compatibility" — while top_k has no tolerated value at all: "models released after Claude Opus 4.6 do not accept top_k; any value will be rejected with a 400 error." OpenAI's reasoning models took the same route earlier and more bluntly: developers porting code report HTTP 400 responses with the code unsupported_value and the message "Only the default (1) value is supported," with some models rejecting the field at any value at all. The pattern across both vendors is identical — the newest models keep the parameter for backward compatibility and refuse to let you use it.

And the replacement is not a smaller dial, it is a different axis. Anthropic's current request schema exposes output_config.effort — low, medium, high, xhigh, max — described as "how much effort the model should put into its response," plus a thinking configuration where Claude "decides when and how much to think" (adaptive) or you set a budget_tokens floor of 1,024 (manual). OpenAI steers the same way with reasoning effort and verbosity. These control how long the model works, not how randomly it samples. For a buyer that is a meaningful shift: the thing you can now tune costs tokens and latency, whereas temperature was free. Where temperature once bought variety at no extra charge, you now buy it with a longer answer and a bigger bill — which is why the inference cost line and the sampling question have become the same conversation.

Which makes prompt instructions the last portable control. The practical migration advice is unglamorous: move the behaviour into the text. Instead of dropping temperature to 0.2 for an extraction job, write the determinism requirement into the instruction — return only values that appear verbatim in the source, do not paraphrase or infer, return null for absent fields. That survives a model swap, a provider migration and a deprecation notice, because it lives in your prompt rather than in someone else's request schema. It is also the only version of the control that works in a consumer product where no parameters are exposed at all — the chat tools in our best AI chatbots ranking.

Quick checklist

  • Never copy a temperature across providers. OpenAI and Google run 0–2 with a default of 1; Anthropic ran 0–1 with a default of 1. The same number is a different percentile on each, and Google's own recommended starting value is 1.0, not a low number.
  • Change temperature or top_p, never both. OpenAI says so directly; Anthropic labels top_p and top_k advanced-only. Two dials at once produce settings no one can reproduce or debug.
  • Do not sell temperature 0 as deterministic. All three vendors state that 0 is not fully reproducible. If you need auditable sameness, pin the model version, log system_fingerprint, and test the output rather than trusting the setting.
  • Check whether the parameter still exists on your model. On models after Claude Opus 4.6 only the default 1.0 is accepted and everything else is a 400; on OpenAI's reasoning models sampling is refused. Move behaviour into the prompt before the migration, not after the incident.
  • Budget for the replacement. Effort and thinking budgets trade money and latency for thoroughness. If your cost model was built when temperature was free, the new control is not free — re-run the estimate with token pricing before you raise it.
  • Watch for low-temperature looping. Google's own guide suggests raising temperature to at least 0.1 when a model gets stuck in infinite generation. If you set 0 for "safety," verify that against real traffic, not intuition.

Where you'll hit it

Every AI tool review on this site implicitly assumes a sampling configuration, because it decides what a "good" answer even looks like: a ChatGPT vs Claude comparison run at each vendor's default is a comparison of two different default distributions, not two different amounts of intelligence. It shows up hardest in three places. Structured extraction, where a single sampled token can turn a number into a paragraph. Agentic loops, where each step samples again and small divergences compound into entirely different tool calls — the reason agent harnesses tend to run cold. And long-context work, where the context window sets what the model can see and temperature sets how adventurous it is about what to say next. Related terms worth reading alongside this one: tokens per second for the speed you get at any setting, reasoning tokens for the output you pay for but never see, and AI hallucination for the failure that temperature is often (wrongly) blamed for. The bottom line

Temperature is a small, honest mechanism with an oversized reputation. It reshapes a probability distribution and nothing else: it does not add knowledge, it does not make output reproducible, and it does not mean the same thing on three providers whose ranges disagree by a factor of two. The 2026 development is that the vendors have started agreeing with that assessment — Anthropic deprecates it on everything released after Claude Opus 4.6, OpenAI's reasoning models refuse any value but the default, and Google tells you to start at 1.0 and raise it if the model loops. What replaces it is not a better dial but a more expensive one: effort and thinking budgets that cost tokens and seconds. So the practical advice for anyone buying an AI tool is to stop treating temperature as a quality setting and start treating it as a portability risk — write your determinism and style requirements into the prompt, check which parameters still exist on the model you just migrated to, and never let a vendor's "temperature 0" claim stand in for a reproducibility test you did not run.
